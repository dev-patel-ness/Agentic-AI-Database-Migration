Two separate things are at play here — worth distinguishing:

## 1. How state flows between agents in *your project's* pipeline

This is handled by `orchestrator/state.py` + `orchestrator/graph.py`, not by any "memory" mechanism per se:

- **Single shared Pydantic model** (`MigrationState`) is the one source of truth. It has typed sub-fields: `discovery`, `plan`, `schema_translation`, `data_migration`, `validation`, `test_report`, `deployment`, etc.
- **LangGraph nodes are pure functions**: each node (e.g. `_discover`, `_validate`) takes the current `state: MigrationState` as input, does its work by calling into an **agent module** (`agents/assessment_agent`, `agents/validation_agent`, …), and returns a **partial dict** of fields to merge back into state (e.g. `{"current_phase": "Discover", "discovery": discovery.model_dump()}`).
- **LangGraph's `StateGraph` merges that dict into the shared state** and passes the updated state object to the next node in the graph. So "agent A talking to agent B" is really: node A writes `state.validation = ...` → graph edge → node B reads `state.validation` as input.
- **Persistence/checkpointing**: `orchestrator/checkpointer.py` (Postgres-backed `BaseCheckpointSaver`) snapshots this state at every node transition. That's what enables resuming a job after a human-review interrupt or a process restart — the next API call reloads state from the DB checkpoint, not from in-memory Python objects.
- **Out-of-band data** (DB connection credentials) deliberately does *not* live in this Pydantic state (secrets shouldn't be checkpointed) — instead `orchestrator/connection_registry.py` holds those in a separate in-process registry keyed by `job_id`, referenced by multiple nodes (Discover, Transform/Schema Agent) during a single run.

So: no agent has "memory" of its own — they're stateless functions; all cross-agent continuity is the single `MigrationState` object + Postgres checkpoints.
